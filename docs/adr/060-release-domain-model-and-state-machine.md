# ADR-060: Release Domain Model and State Machine

- **Status**: Proposed
- **Date**: 2026-09-02
- **Supersedes**: None
- **Scope**: Typed release identities, single-target jobs, stages, candidates, progress, diagnostics, terminal results, concurrent observation, cancellation and presentation-independent ownership
- **Issue**: [REL-001.1](https://github.com/abdullahbodur/horo-engine/issues/184)
- **Jira**: [HORO-184](https://horo-engine.atlassian.net/browse/HORO-184)
- **Parent**: [REL-001](https://github.com/abdullahbodur/horo-engine/issues/36)
- **Related**: [ADR-001](001-native-ci-builds.md), [ADR-003](003-artifact-identity.md), [ADR-004](004-cli-core-gui-boundary.md), [ADR-008](008-error-model-exception-boundary-and-registry.md), [ADR-010](010-job-waiting-and-operation-store-ownership.md)
- **Normative documents**: [Release Architecture](../architecture/release/release.md), [Release Security](../architecture/release/release-security.md), [Engine Data Bus](../architecture/foundation/engine-data-bus.md), [Observability Architecture](../architecture/observability/observability.md)

## Context

GUI, CLI, MCP and CI must submit and observe one release service. The current
release architecture describes a single `Pending -> Validating -> ... ->
Succeeded` sequence, but that sequence conflates three different concerns:

- job ownership, cancellation and immutable target identity;
- ordered pipeline stage attempts and progress.

That ambiguity makes matrix aggregation, cancellation races, observer lifetime
and partial candidate evidence difficult to define. It also invites a modal,
terminal process or CI adapter to own a job merely because it presented the
submission. A release result must preserve the exact target and stage that failed,
the stable error cause and diagnostic identities, even after the initiating UI
surface closes.

The release domain model therefore needs one state authority, legal transitions,
immutable revisioned snapshots and exactly one terminal result before later
profile, planning, target, staging, signing, recovery and publication work begins.

## Decision

### 1. Identities are typed and never inferred from paths or presentation

The domain uses distinct bounded identities:

```cpp
struct ReleaseJobId;
struct ReleaseGroupId;
struct ReleaseTargetId;
struct ReleaseStageAttemptId;
struct ReleaseCandidateId;
struct ReleaseSnapshotRevision;
struct ReleaseEventSequence;
struct DiagnosticId;
```

`OperationId` is reused from the shared operation system. A release job records
its associated operation ID, but the two are not interchangeable: the release
service owns release state and the operation store owns cross-use-case activity
projection.

`ReleaseTargetId` identifies one frozen operating-system, architecture,
configuration, product-profile and toolchain-plan entry within a job. A display
label, output path, matrix index or platform enum is not target identity.

`ReleaseCandidateId` identifies finalized immutable candidate bytes and metadata.
It is not a job ID, version, tag, output directory or publication identity. A job
may fail during final verification or publication while still preserving a
candidate reference and its ineligible/verified state.

IDs are generated by their owning service/store, are never reused, and are safe
to log. Secret handles and raw credentials are not identities in this model.

### 2. Submission creates a service-owned single-target job

Every adapter submits the same typed request:

```cpp
struct ReleaseRequest {
    ProjectIdentity project;
    ProductVersionRequest version;
    ReleaseProfileRequest profile;
    ReleaseTargetRequest target;
    ReleaseOutputRequest output;
    ReleaseSecurityRequest security;
    ReleasePublicationRequest publication;
    ReleaseDiagnosticsOptions diagnostics;
};

enum class ReleaseGroupRequirement {
    Required,
    Optional,
};

struct ReleaseGroupMemberRequest {
    ReleaseRequest request;
    ReleaseGroupRequirement requirement;
};

struct ReleaseGroupRequest {
    std::vector<ReleaseGroupMemberRequest> members;
};

struct ReleaseGroupMembership {
    ReleaseGroupId group;
    ReleaseGroupRequirement requirement;
};

struct ReleaseSubmission {
    ReleaseJobId job;
    OperationId operation;
    std::optional<ReleaseGroupMembership> group;
    ReleaseSnapshotRevision initialRevision;
};

struct ReleaseGroupSubmission {
    ReleaseGroupId group;
    std::vector<ReleaseSubmission> jobs;
};
```

Request fields are typed intent, not an execution plan. Paths are normalized at
the owning boundary, credential fields are opaque handles, and adapter-specific
transport fields do not enter the request. The immutable preflight plan and its
input freeze are owned by
[REL-001.4](https://github.com/abdullahbodur/horo-engine/issues/178).

`ReleaseService::Submit` validates bounded request shape, allocates the job and
operation records, publishes the initial snapshot, and then admits execution. A
standalone submission has no group membership. `ReleaseService::SubmitGroup`
validates a bounded non-empty member set, allocates one service-owned
`ReleaseGroupId`, and atomically creates every independent job with immutable
required/optional membership. An adapter never invents a group ID or reconstructs
membership from target labels, request order, timestamps or paths.

A returned `ReleaseSubmission` or `ReleaseGroupSubmission` is a value handle for
queries and cancellation; its destruction does not cancel or release any job.

### 3. Job state and stage state are separate

The job state is:

```cpp
enum class ReleaseJobState {
    Queued,
    Running,
    Cancelling,
    Succeeded,
    Failed,
    Cancelled,
};
```

One `ReleaseJobId` executes exactly one frozen `ReleaseTargetId`. A target matrix
submission produces one group plus independent jobs, each with immutable
required/optional membership. Matrix summaries query by `ReleaseGroupId` and are
derived from the complete membership set and job snapshots; they do not replace,
merge or rewrite per-target terminal results. Adapters cannot aggregate arbitrary
jobs or omit a required member.

Pipeline work uses a separate ordered stage model:

```cpp
enum class ReleaseStage {
    Validating,
    Configuring,
    Building,
    Cooking,
    Packaging,
    PreSignVerifying,
    Signing,
    FinalizingMetadata,
    FinalVerifying,
    Publishing,
};

enum class ReleaseStageState {
    NotStarted,
    Running,
    Succeeded,
    Failed,
    Cancelled,
    NotApplicable,
};
```

The frozen plan contains the stage sequence and marks optional work such as
signing or publication `NotApplicable` before execution. Runtime skipping by
silently jumping over a stage is forbidden. Each execution has a unique
`ReleaseStageAttemptId`; retry creates a new attempt and never rewrites the prior
attempt's result.

### 4. Legal transitions are closed and deterministic

Job state accepts only:

| From | Legal next states |
| --- | --- |
| `Queued` | `Running`, `Cancelled`, `Failed` |
| `Running` | `Cancelling`, `Succeeded`, `Failed` |
| `Cancelling` | `Cancelled`, `Failed` |
| `Succeeded` | none |
| `Failed` | none |
| `Cancelled` | none |

A queued job whose worker admission has not committed may transition directly to
`Cancelled`, atomically storing its cancellation result; it owns no pipeline
resource that requires asynchronous cleanup. If admission wins the serialized
race, the job is `Running` and cancellation must proceed through `Cancelling`
until cleanup acknowledges cancellation or fails. A start/admission failure may
transition directly from `Queued` to `Failed` with no fabricated running stage.

Stage attempts accept only:

| From | Legal next states |
| --- | --- |
| `NotStarted` | `Running`, `NotApplicable` |
| `Running` | `Succeeded`, `Failed`, `Cancelled` |
| `Succeeded`, `Failed`, `Cancelled`, `NotApplicable` | none |

A stage may begin only when every required predecessor succeeded. A job may
succeed only when every planned required stage succeeded and all other stages are
`NotApplicable`, and candidate policy is satisfied. A matrix summary may report
success only when every required independent job succeeded. One failed required
job cannot be hidden by a successful sibling.

Repeated, backwards, duplicate-terminal and post-terminal transitions return a
typed `IllegalReleaseTransition` error containing job, optional target, optional
attempt, expected state set and observed revision. They do not emit a second
event, change timestamps or overwrite the original result.

### 5. Exactly one terminal result is committed

Every job record owns one optional terminal variant:

```cpp
using ReleaseTerminalResult = std::variant<
    ReleaseSucceeded,
    ReleaseFailed,
    ReleaseCancelled>;
```

The terminal result is absent in `Queued`, `Running` and `Cancelling`, and present
exactly once in the matching terminal state. State and result commit atomically in
one service mutation. A terminal snapshot without a result, or a non-terminal
snapshot with one, is invalid.

`ReleaseSucceeded` contains the immutable target identity, completed stage
attempts and eligible candidate ID.
`ReleaseFailed` contains:

- the failed job and target ID;
- the failed stage and attempt ID when execution reached a stage;
- the stable Horo `Error` cause;
- bounded ordered `DiagnosticId` references;
- any finalized candidate ID and its verification state.

`ReleaseCancelled` contains the accepted cancellation identity/time, the last
active stage attempt, completed stage attempts, diagnostics and any candidate that
already existed. Cancellation is an outcome, not an error string.

The service serializes mutations per job and applies one compare-and-commit rule.
If success commits before cancellation is accepted, a later cancel request returns
`AlreadyTerminal`. If cancellation is accepted first, no later stage starts and
ordinary completion cannot commit success. A failure that prevents safe cleanup
while cancelling commits `Failed` with cancellation evidence; it is not reported
as clean cancellation. The detailed recovery implementation is owned by
[REL-001.17](https://github.com/abdullahbodur/horo-engine/issues/194).

### 6. Candidates have state independent from job outcome

Finalizing metadata freezes candidate bytes and assigns `ReleaseCandidateId` with
state `Finalized`. Final verification may advance the candidate to
`FinalVerified`; no other mutation of its artifacts or canonical manifest is
allowed. Failed verification retains the finalized identity as ineligible
evidence and never publishes it.

Publication consumes a `FinalVerified` candidate. A publication failure makes the
release job fail at `Publishing` but does not invalidate or rebuild the candidate.
Retry or repair refers to the same candidate through a new publication attempt or
job according to publication policy.

Candidate storage owns candidate records and immutable artifact leases. A release
job snapshot refers to them by ID and verification state; it does not own files by
path or delete candidate bytes when an observer disappears.

### 7. Snapshots are the observation authority

`ReleaseService` exposes immutable bounded snapshots:

```cpp
struct ReleaseJobSnapshot {
    ReleaseJobId id;
    OperationId operation;
    std::optional<ReleaseGroupMembership> group;
    ReleaseSnapshotRevision revision;
    ReleaseJobState state;
    ReleaseRequestSummary request;
    ReleaseTargetSnapshot target;
    ReleaseProgressSummary progress;
    std::vector<DiagnosticId> recentDiagnostics;
    std::optional<ReleaseTerminalResult> terminal;
};
```

Every successful mutation increments a job-local monotonic revision. Querying by
job ID returns one internally consistent snapshot; observers never assemble state
from independent mutable fields. Collections and diagnostic summaries have fixed
service limits and deterministic ordering.

Querying a `ReleaseGroupId` returns its immutable complete membership plus the
latest snapshot for every member in canonical target-ID order. Group success is a
pure derived result: every required member succeeded and no required member is
missing; optional failures remain visible but do not rewrite any job result.

Submission, active, recent and retained terminal queries all use the same domain
snapshot. Retention/archival may remove a completed snapshot only under explicit
policy; queries then return typed `ReleaseJobExpired` or an archive reference,
never a newly synthesized empty result.

### 8. Events are bounded invalidations, not a second state store

Progress and lifecycle events include job ID, snapshot revision, event sequence,
optional target/stage attempt, typed progress units and diagnostic IDs. They do
not carry raw logs, unbounded process output, whole mutable snapshots or secrets.

Events may be coalesced for presentation. On any event, reconnect or detected
sequence gap, an observer queries the latest snapshot. The event bus is therefore
not authoritative and event loss cannot corrupt release state.

Subscription establishes a race-free baseline: the service returns a snapshot
and subscription token from one observation operation, ensuring the observer sees
either that revision or a later invalidation. Tokens are move-only RAII values;
releasing one detaches only that observer.

Logs and complete diagnostics remain in service-owned bounded stores keyed by job,
target and stage attempt. Snapshots carry identities and summaries rather than
duplicating output.

### 9. The service, not presentation, owns lifetime

| Owner | Responsibility |
| --- | --- |
| `ReleaseService` | Job record, transition authority, cancellation source, operation association, pipeline task, snapshot/history retention and terminal commit |
| `ReleasePipeline` | Execute one frozen plan, report typed stage mutations and return owned stage resources on every path |
| Stage worker/provider | Child process, credential lease, temporary output and other resources for one attempt until handed back or cleaned up |
| Candidate store | Finalized immutable candidate metadata/artifact leases and verification state |
| Operation store | Cross-use-case activity projection and bounded progress/result references, not release state authority |
| GUI/CLI/MCP/CI adapter | Validate transport input, submit, query/observe, present and request cancellation |

Closing `BuildReleaseModal`, losing an MCP client, exiting an observing CLI
process or finishing a CI log view releases subscriptions only. It does not
cancel, terminalize, erase or orphan the job. Cancellation is an explicit
idempotent service request authorized for that job.

Service shutdown closes submission, requests cancellation for service-owned
active jobs, drains or persists them according to recovery policy, commits one
terminal/recoverable state and only then destroys pipeline resources. Adapter
destruction is never the shutdown mechanism.

### 10. Adapters cannot reinterpret state

GUI, CLI, MCP and CI use the same request, snapshot, transition, diagnostic and
terminal-result contracts. They may translate typed results to UI, JSON, protocol
errors or exit codes, but cannot:

- infer success from progress reaching 100%;
- report one target job success as matrix success;
- treat `Cancelling` as terminal `Cancelled`;
- turn a failed final verification into a candidate;
- drop target/stage/cause/diagnostic identity from machine-readable output; or
- create adapter-local retries that rewrite a stage attempt.

### 11. Contract verification is mandatory

The domain/state-store contract suite covers at least:

- the complete legal transition table and rejection of every illegal edge;
- duplicate, backwards and post-terminal mutations with unchanged revision;
- exactly one terminal result per job;
- success, stage failure, pre-stage failure, cancellation and cleanup failure;
- cancel/completion, failure/cancel and shutdown/completion races under controlled
  scheduling;
- formal group identity/membership, mixed independent target-job results and
  required/optional matrix aggregation;
- result preservation of target, stage, attempt, error and diagnostic identities;
- candidate finalized, final-verified, verification-failed and publication-failed
  outcomes;
- concurrent query/observe with monotonic revisions and event coalescing/gaps;
- modal/subscription destruction while the job remains queryable;
- service shutdown with queued, running and cancelling jobs; and
- bounded snapshot, event, diagnostic and retention behavior.

Tests use deterministic fake clocks, ID sources, pipeline drivers and event sinks.
They do not depend on real compiler, signing, network or GUI timing to prove the
state machine.

## Compatibility And Migration

The current release document's single stage-named job state is a presentation
projection, not the new domain model. Migration maps:

- `Pending` to job `Queued`;
- any active stage-named state to job `Running` plus one running
  `ReleaseStageAttempt`;
- terminal success/failure/cancellation to the matching typed terminal variant;
- legacy build-history job arrays to read-only migration input, never live state;
  and
- modal-local progress/log ownership to service snapshot and store queries.

Legacy records missing stable target, stage attempt, cause or diagnostic identity
remain explicitly `LegacyIncomplete`; migration does not invent evidence. New
writers emit only the revisioned typed model. Version, profile, frozen-plan,
candidate-manifest and publication schema details remain owned by their focused
REL-001 tickets.

## Consequences

- Target and per-stage status is unambiguous, and one target's result cannot be
  presented as matrix success.
- A release remains observable across UI, protocol and process presentation
  lifetimes.
- Cancellation and completion races have one serial authority and one terminal
  result.
- Snapshots support simple concurrent readers while bounded invalidation events
  avoid duplicating state in the data bus.
- Candidate evidence survives publication failure without allowing an unverified
  artifact to become eligible.
- The service must maintain revisioned state, retention, generation-safe
  subscriptions and deterministic test drivers in addition to pipeline work.
- Retry is explicit new-attempt history rather than mutation of prior evidence,
  increasing record volume but preserving attribution.

## Rejected Alternatives

| Alternative | Reason rejected |
| --- | --- |
| Use the current stage enum as the job state | Conflates ownership, immutable target identity and pipeline position; cannot represent cancelling or retries cleanly. |
| Let each adapter own its submitted job | Closing a modal/client would cancel or orphan work and produce different GUI/CLI/MCP/CI semantics. |
| Treat progress events as authoritative state | Event loss, coalescing and subscriber timing would create inconsistent results. |
| Use one string status/result map | Cannot enforce legal transitions, terminal invariants or stable failure identity. |
| Overwrite a stage result on retry | Destroys evidence and makes diagnostics/artifacts unattributable to the attempt that produced them. |
| Make running-job cancellation immediately terminal | Resources and child work may still be active; `Cancelling` must remain observable until cleanup or failure commits. Queued jobs not yet admitted may commit `Cancelled` directly. |
| Delete a candidate when publication fails | Publication is separate from immutable candidate construction; retry must not rebuild verified bytes. |
