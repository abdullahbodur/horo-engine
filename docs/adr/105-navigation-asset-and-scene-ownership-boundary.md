# ADR-105: Navigation Asset and Scene Ownership Boundary

- **Status**: Proposed
- **Date**: 2026-09-02
- **Supersedes**: None
- **Scope**: Grounded navigation definition assets, authored Scene intent, bake-input capture, cooked NavMesh artifacts, stable identity and provenance, mutation authority, runtime topology, missing-data behavior, migration and non-ground navigation separation

## Context

ADR-016 assigned backend-neutral navigation contracts and runtime policy to Horo,
and ADR-104 selected Recast/Detour as the first private grounded NavMesh provider.
Those decisions do not yet say which navigation values are authored, which are
captured from a Scene, which are generated by bake, or which exist only while a
runtime world is active.

Without that separation an editor could serialize generated polygons into a Scene,
a runtime system could treat a provider tile reference as durable identity, or a
stale cook could appear current after its collision geometry changed. These paths
create competing sources of truth and make source migration, cache invalidation,
provider replacement and world streaming unsafe.

Navigation also needs multiple grounded agent profiles and tiled output without
inventing one Asset Registry identity per generated tile. At the same time,
diagnostics must trace every polygon back to stable authored contributors. Runtime
must distinguish missing data from an unreachable route and cannot hide either by
baking, loading source files or returning a straight-line path.

This ADR freezes the representation and ownership boundaries. NAV-003 may define
the detailed bake transaction and cache implementation, and NAV-004 may refine
query snapshot contracts, but neither may merge these authorities.

## Decision

### 1. Navigation has four representations with one-way derivation

| Representation | Durable authority | Owner | May be edited | Runtime input |
|---|---|---|---:|---:|
| `NavigationDefinition` plus typed Scene navigation components | Yes, project source | Navigation authoring domain and `SceneDocument` | Yes, through document/asset transactions | No |
| `NavigationBakeInputSnapshot` | No, immutable derived capture | Bake operation | No | No |
| `GroundedNavMeshArtifact` exposed as neutral `NavMeshData` | Derived immutable cooked generation | Asset Pipeline publication; Navigation cooker semantics | No | Yes |
| `NavigationTopologySnapshot` plus overlays/query state | No, generation-scoped runtime state | NavigationRuntime and selected provider | Only through runtime commands | Active-world only |

The only legal flow is:

```text
NavigationDefinition + SceneDocument + exact geometry artifacts
    -> NavigationBakeInputSnapshot
    -> GroundedNavMeshArtifact / cell NavigationMesh payload
    -> NavigationTopologySnapshot
```

No reverse edge exists. Generated regions, contours, polygons, adjacency, tiles,
provider bytes, runtime handles, crowd state and obstacle-carving results are never
written into a `SceneDocument` or `NavigationDefinition` as authored truth. An
editor visualization reads an immutable candidate or published artifact and draws
a projection; selecting or moving debug polygons does not edit them.

### 2. Project and Scene source store intent, not generated topology

`NavigationDefinition` is the authoring representation of a tracked `core.navmesh`
asset with the single Asset Registry `AssetId` from its sidecar. It owns:

- grounded agent profiles and stable `GroundedAgentProfileId` values;
- build settings, tile/coordinate conventions and deterministic source policy;
- stable `NavigationAreaId` definitions, traversal costs and filter defaults; and
- declared bake scopes and required capability/profile policy.

A Scene references that definition by `AssetId` and expresses object-local intent
through typed components:

- `NavigationSurfaceComponent` selects the definition, grounded profiles and bake
  scope for a stable Scene object;
- `NavigationSourceComponent` explicitly includes accepted collision geometry and
  assigns area/source policy;
- `NavigationModifierComponent` contributes an area, exclusion or cost volume;
- `NavigationLinkComponent` owns a stable `NavigationLinkId` and an explicit
  grounded transition such as jump, ladder, door or teleport; and
- `NavigationObstacleComponent` declares runtime dynamic-obstacle intent without
  pretending its carved topology is authored.

These names define typed semantic roles; implementation may group their payloads
where the same ownership and schema remain visible. Components carry stable Horo
IDs, transforms, references, settings and semantic intent. They never carry
triangles copied from another asset, cooked polygon arrays, provider flags,
`dtPolyRef`, `dtTileRef`, provider blobs or runtime topology handles.

Geometry authority remains with the owning mesh, terrain or collider description.
Navigation consumes an exact, validated canonical geometry snapshot through a
host-composed read-only cook adapter; it does not depend on a runtime Physics world
or solver-native shape. A Physics-owned normalized source model may supply that
snapshot under ADR-085. Render meshes are not implicit navigation input. A project
may explicitly select an accepted render-derived source only through a typed source
policy whose conversion, scale and provenance become cook inputs.

All authored mutation occurs through the owning asset or Scene document
transaction. Editor panels, viewport tools, CLI and MCP are adapters to those same
commands; they do not write cooked/cache files or private provider state directly.

### 3. Stable authored identity and runtime identity are disjoint

Durable identities are:

- the navigation definition's existing `AssetId`;
- stable `GroundedAgentProfileId`, `NavigationAreaId` and `NavigationLinkId` values;
- the Scene asset identity plus stable `SceneObjectId` and component identity; and
- a stable `NavigationContributionId` where one component emits multiple distinct
  source contributions.

The canonical source-contribution key is built from the owning Scene asset/scope,
stable object/component identity and optional contribution identity. It is never
built from an entity slot, component-pool address, source path, display name,
iteration index or worker completion order. Rename, file move and runtime entity
reallocation therefore do not silently change semantic identity.

Generated tiles do not receive new authoring `AssetId` values or sidecars. One
navigation cook product is rooted at the source definition `AssetId`; its internal
partition key contains stable bake scope, `GroundedAgentProfileId`, tile
coordinate/layer, typed target/profile, format version and content digest. These
partition keys are not Asset Registry identities. ADR-023 cell payloads retain that
provenance; they are packaging/residency projections of the same cook output, not
separate navigation assets.

`NavigationWorldId`, topology generation, provider instance identity,
`NavigationTileHandle`, query handles, obstacle handles and provider polygon refs
are runtime-only generation-checked identities. They are never serialized into
project source, cooked neutral identity, save games or network protocols.

### 4. Bake captures one immutable, revision-consistent input snapshot

The application-owned bake operation captures one bounded
`NavigationBakeInputSnapshot` only after project/source migration and validation.
The snapshot contains:

- exact project and persistent-contract versions;
- navigation definition `AssetId`, source digest, schema and revision;
- one immutable Scene document revision and stable bake-scope identity;
- canonically ordered contributing object/component IDs and semantic payloads;
- exact collision/source artifact identities, revisions and content digests;
- grounded profile, area/link tables, build settings and coordinate/origin policy;
- pinned Asset Registry, package lock and contribution-catalog revisions; and
- cooker/provider/adapter identity, schema and execution fingerprints.

Capture resolves authoring references and transforms into owned immutable bounded
data. Workers never retain `SceneDocument`, ECS, registry, asset-record or mutable
geometry pointers. Canonical ordering is by typed stable key, not source container
or job order. Non-finite values, ambiguous contributors, unsupported source kinds,
missing geometry, duplicate stable IDs, incompatible scale/coordinate policy or a
changed captured revision reject the candidate.

The snapshot is ephemeral derived state. It may be content-addressed for bounded
cache reuse, but it is not registered as an asset, packaged, edited, migrated or
loaded by runtime. Reopening an editor reconstructs it from durable source.

### 5. The cooked artifact carries complete provenance and no authoring authority

Navigation cook transforms an accepted snapshot into a bounded immutable
`GroundedNavMeshArtifact`. The standard Asset Pipeline envelope and dependency-
aware key include every semantic input from the capture, the neutral
`navMeshFormatVersion`, target/profile, coordinate and tile schema, cooker version,
and the exact ADR-104 provider fingerprint when provider-private sections exist.

The neutral payload contains validated grounded vertices, polygons, adjacency,
areas, off-mesh links, bounds, tiles and source-contribution provenance sufficient
for diagnostics. Provenance maps generated ranges to stable contributors and exact
input digests; it does not copy editor history or retain source paths as identity.
Provider-native optimized sections are optional, separately versioned and
fingerprinted. They are discarded on mismatch and never become the portable
semantic authority.

Only the host Asset Pipeline may stage, validate and atomically publish the
candidate cooked generation. The Navigation cooker emits bounded logical output
through host-owned writers; it cannot choose paths, update `current.json`, invent
sidecars or mutate the active provider. Cancellation, stale capture, malformed
output, dependency change, cache mismatch or publication failure preserves the
last valid generation.

Cooked data is persistent build output but is not durable project truth. Deleting
it loses no authored intent. It is rebuilt from the exact source snapshot and never
hand-edited, patched by the editor or migrated as if it were a Scene document.

### 6. Runtime owns materialization, topology generations and transient overlays

Scene conversion resolves required definition/profile/scope references to exact
published artifact identities and expected digests. Runtime preparation validates
the neutral envelope, provenance bounds, requested target/profile, provider
compatibility and all required tile payloads before constructing a detached
`NavigationTopologySnapshot`.

The snapshot binds one `NavigationWorldId`/scene incarnation, topology generation,
origin policy, loaded tile set and immutable artifact leases. The selected provider
owns private decoded/native resources underneath that snapshot. Publication joins
the Scene or World Streaming activation transaction and becomes visible only at the
declared lifecycle safe point; queries never observe a partially installed mesh.

NavigationRuntime separately owns bounded query scratch/cache, logical obstacle and
crowd state, and immutable overlay revisions. Dynamic carving produces a candidate
runtime topology generation derived from the active cooked base plus logical
obstacle commands. It does not mutate or republish the cooked artifact. A desired
persistent obstacle/modifier change must first commit a Scene document command and
then produce a new cook.

Reload creates a detached candidate from a new published artifact. Successful
activation swaps generations atomically and retires old provider resources only
after all query/tile leases drain. No runtime state writes back to source or selects
an unverified inactive cook generation.

### 7. Missing, stale and unsupported data fail explicitly

The following outcomes are distinct typed failures:

- missing navigation definition, profile, source contribution or geometry artifact;
- missing or corrupt cooked artifact/tile;
- stale source, dependency, registry, project, schema or cook fingerprint;
- unsupported neutral/provider format or required capability; and
- valid topology with no reachable route.

Runtime never opens authoring files, imports geometry, invokes Recast, migrates a
source, downloads a provider, selects an older inactive generation or returns a
straight-line path to hide these outcomes. `NavigationNull` keeps ADR-016 semantics:
queries return `NoNavigationData`, never fake success.

Editor/CLI diagnostics may identify the stable contributor and offer an explicit
bake operation. They may keep displaying the last valid generation as visibly
stale reference material, but preview/play admission cannot label it current. A
release cook/package fails when required navigation closure is absent or stale.

Scene activation fails atomically when navigation is declared required. An
explicitly optional navigation capability may activate with `NoNavigationData` and
observable diagnostics; optional does not authorize fallback topology. For World
Streaming, an absent required cell NavigationMesh payload blocks cell activation.
A temporarily nonresident neighboring tile may cause a bounded residency request
and explicit partial/no-data query result under ADR-012; Navigation does no direct
I/O and does not change cell authority.

### 8. Source migration and derived invalidation are separate

`HoroProjectVersion` governs `NavigationDefinition`, Scene navigation components,
stable IDs and their typed payloads. Supported older authored schemas are migrated
through the normal project-open transaction before a writable session exists.
Migration preserves retained stable identities or records an explicit reviewed
mapping; it cannot silently replace an ID and orphan diagnostics/references.

Legacy source containing embedded generated polygons, provider refs or tile blobs
is handled by an explicit one-time recipe. The recipe extracts only recoverable
semantic intent into a definition/component model, records any fidelity loss and
discards generated/native bytes. If the original intent cannot be reconstructed,
the migration blocks with a typed diagnostic instead of blessing generated data as
source truth.

Cooked navigation outputs, bake snapshots, provider sections, caches, cell
NavigationMesh blocks and runtime topology are invalidated and rebuilt, not source-
migrated. A changed project/schema/source/collision digest, coordinate policy,
provider fingerprint or cook format deterministically invalidates affected output.
Unsupported newer source blocks open; unsupported cooked data requests recook or a
compatible engine and never mutates project source.

### 9. The 1.0 model is tiled grounded-surface navigation

The `GroundedAgentProfileId` schema describes grounded clearance and traversal:
radius, height, climb/step, slope and related surface/filter policy. Multiple
profiles may produce separate layers or tiles from the same bake scope, while
retaining exact profile provenance.

Flying, swimming, space and other free-volume movement do not use a permissive
grounded profile, a special area flag or hidden link convention. They require a
future distinct authoring component/asset, provider capability, cooked artifact and
query result model. Directed road/rail/lane navigation likewise remains a separate
graph domain. Off-mesh links join explicit transitions between grounded surfaces;
they do not turn a NavMesh into a volumetric representation.

### 10. Qualification proves ownership and failure boundaries

Required evidence includes:

- source edits through document transactions while generated polygons/tiles remain
  immutable and absent from authored Scene serialization;
- stable ID preservation across rename/move/reorder and deterministic contributor
  identity independent of entity slots, paths and worker order;
- snapshot consistency under concurrent Scene/asset changes, cancellation, bounds
  and stale-completion rejection;
- dependency-aware invalidation for every definition, Scene, collision, profile,
  area/link, coordinate, schema, cooker and provider fingerprint input;
- byte-identical neutral artifacts for identical qualified inputs and canonical
  tile/profile/contributor ordering;
- cache/output corruption, partial staging and publication failure retaining the
  prior valid generation;
- runtime validation, atomic Scene/cell activation, generation-safe reload and
  delayed provider/tile retirement under in-flight queries;
- authored dynamic obstacle intent versus transient carving, with no cooked/source
  mutation and deterministic stale-overlay rejection;
- distinct missing/stale/unsupported/unreachable outcomes, required versus optional
  activation policy and no runtime cook/source-I/O/fake-path fallback;
- migration of retained semantic intent, invalidation of all generated/native data
  and fidelity diagnostics for unrecoverable legacy inputs; and
- rejection of flying/swimming/volumetric and lane semantics from grounded profiles
  while ordinary grounded multi-profile and off-mesh-link cases remain valid.

## Consequences

### Positive

- Authored intent has one durable authority and generated topology is always
  replaceable derived data.
- Stable Horo identities survive file moves, runtime entity allocation and provider
  replacement while preserving useful source-to-polygon diagnostics.
- Exact snapshots and provenance make stale cook detection and cache invalidation
  reviewable.
- Runtime loading, dynamic carving and World Streaming share generation/lease rules
  without gaining source or cook authority.
- Grounded 1.0 scope cannot silently absorb incompatible volumetric or lane models.

### Costs

- Scene conversion and bake capture need typed component schemas, canonical source
  extraction and full dependency provenance.
- Navigation artifacts carry additional identity, digest and diagnostic tables.
- Editor tooling must project immutable generated data and route every persistent
  change back through source commands and recook.
- Legacy embedded/generated navigation data may require a lossy, explicitly
  reviewed migration rather than direct preservation.

## Rejected Alternatives

### Store generated polygons and tiles in the Scene document

Rejected because Scene edits, geometry changes and provider upgrades would create
two conflicting authorities. Large generated payloads would also enter undo,
migration and source-control paths without preserving the inputs that produced them.

### Give every profile or tile a new AssetId and sidecar

Rejected because generated partitions are variants of one definition/scope cook,
not independently authored assets. Proliferating IDs would make regeneration look
like deletion/recreation and break stable dependency/provenance semantics.

### Bake automatically at runtime when data is missing

Rejected because runtime packages may not contain Recast, source geometry, project
migrations or write authority. It would add unbounded work and make client/server
and deterministic behavior depend on local timing and source availability.

### Treat collision or render geometry as implicit navigation input

Rejected because invisible inclusion rules make cache identity, author intent,
performance and missing-data diagnostics ambiguous. Inputs are explicit typed
contributions with exact artifact provenance.

### Persist carved runtime topology as the new cooked base

Rejected because dynamic obstacle state belongs to an active world generation and
may be authority-, tick- and residency-dependent. Persistent intent must be applied
to authored components and recooked through the normal transaction.

### Migrate provider-native or generated bytes in place

Rejected because those bytes are derived under exact source, schema, build and
provider fingerprints. Rebuild is safer and preserves the rule that project
migration transforms only durable authored truth.

### Model flying and swimming as grounded agent profiles

Rejected because free-volume reachability has different topology, source, cost,
streaming and query semantics. A grounded profile cannot truthfully express it.
